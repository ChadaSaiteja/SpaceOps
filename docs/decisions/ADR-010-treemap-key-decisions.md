# ADR-010: Treemap Visualization — Key Design Decisions

## Status

Accepted

## Context

Phase 4 introduces the primary interactive visualization of the application: the Treemap. Given an in-memory `StorageTree` (Phase 3) that can contain hundreds of thousands or millions of filesystem nodes, the treemap must visually partition rectangular screen space proportional to disk usage, support smooth 60/120 FPS rendering and resizing, and provide responsive drill-down, hover, selection, and breadcrumb navigation.

This builds on ADR-001 (Rust/C# FFI boundaries), ADR-003 (module boundaries), ADR-007 (threading), and ADR-009 (StorageTree arena and two-handle lifecycle).

---

## Decisions

### 1. Rust-side squarified layout calculation engine

**Decision:** Layout calculation (geometry partitioning) is performed in the Rust core, not in C# managed code. The Rust layout engine takes viewport dimensions `(width, height)`, a root `NodeId`, maximum display depth, and a minimum pixel threshold (e.g. 3 px). It produces a flat contiguous array of `TreemapRectFfi` structs.

**Reason:** 
- Performance: Layout calculation for thousands of nodes runs in $< 2\text{ ms}$ in native Rust with zero garbage collection overhead.
- Direct cache locality: Rust already holds the contiguous `StorageTree` arena (`Vec<TreeNode>` and pre-sorted child indices from ADR-009). C# would have to repeatedly query child arrays across FFI to do layout.
- Decoupling: Keeps layout logic pure, highly testable with unit tests in Rust, and agnostic to the UI framework.

### 2. Win2D / Direct2D immediate-mode rendering in WinUI 3

**Decision:** The WinUI 3 application renders the treemap using Win2D (`Microsoft.Graphics.Win2D`) on a `CanvasControl` (Direct2D hardware-accelerated immediate mode), rather than retained-mode XAML visual tree elements (`Border`, `Grid`, `Canvas`).

**Reason:**
- WinUI XAML visual trees degrade severely when hosting $> 1,000$ interactive UI elements (high memory, layout thrashing during resize, stuttering animations).
- Win2D renders tens of thousands of filled rectangles, antialiased borders, text labels, and highlights in a single draw pass at 60/120 FPS with minimal memory overhead.
- Hit testing for hover and selection is computed via simple point-in-rect checks against the cached layout array in C#, avoiding XAML input routing overhead.

### 3. Squarified treemap tiling algorithm (Bruls, Huizing, van Wijk)

**Decision:** Implement the classic squarified treemap algorithm. Nodes are placed row-by-row along the shorter remaining dimension of the enclosing rectangle, minimizing the maximum aspect ratio ($\max(w/h, h/w)$) to produce tiles as close to squares ($1:1$) as possible.

**Reason:**
- Square tiles maximize usable area for text labeling and are easiest for human eyes to compare in size.
- Avoids the extreme aspect ratio slivers generated by slice-and-dice algorithms, which are unreadable and difficult to click.

### 4. Level of detail (LOD) and pixel culling

**Decision:** 
1. **Pixel Culling:** Any child rectangle whose computed area is smaller than $3 \times 3\text{ pixels}$ (or width/height $< 2\text{ px}$) is omitted or aggregated into an "other / tiny items" bucket.
2. **Visual Depth Limit:** By default, layout calculates down to 2 levels of subdirectories below the current drill-down root.
3. **Drill-down:** When the user double-clicks a directory, it becomes the new drill-down root, recalculating the layout for its immediate subtree in $< 1\text{ ms}$.

**Reason:** 
A screen has $\sim 2\text{ million}$ pixels ($1920 \times 1080$). Displaying 1M nodes at once is physically impossible and visually useless. Pixel culling and depth limits keep the rendered rectangle count between 200 and 2,000 tiles at any time, ensuring instant rendering and readable labels.

### 5. Categorical color palette with luminance depth variations

**Decision:** Rectangles are color-coded by file category (PRD §8: Videos, Audio, Documents, Images, Archives, Executables, System, Code, Other). Directories can optionally be drawn with subtle container borders or tinted by their dominant category. Hovered and selected items receive high-contrast highlight borders.

**Reason:**
- Matches PRD §8's categorization requirements.
- Enables instant visual recognition of what kind of data dominates disk usage (e.g. large purple blocks for video, green for archives).

### 6. Interactive navigation model (Drill-down, Breadcrumbs, Selection)

**Decision:**
- **Single click:** Selects a node, highlights its rectangle, and notifies the Details Panel.
- **Double click:** Drills down into a directory, updating the root `NodeId` and breadcrumbs.
- **Breadcrumb Bar:** Displays the path of drill-down ancestors (e.g. `C:\ > Users > Saiteja > Downloads`), enabling 1-click navigation back to any parent.
- **Hover:** Updates tooltip and status bar with filename, formatted size, and percentage of parent.

---

## Consequences

### Positive
- Blazing layout performance: $< 2\text{ ms}$ layout calculations in Rust.
- 60/120 FPS rendering in WinUI 3 using hardware-accelerated Win2D.
- Zero managed memory allocations during window resize or panning.
- Clear separation of concerns: Rust computes geometry, Win2D draws pixels, WinUI handles windowing and user input.

### Negative
- Requires adding `Microsoft.Graphics.Win2D` NuGet dependency to `StorageIntelligence.csproj`.
- Window resize triggers an FFI layout call (though at $< 0.5\text{ ms}$, this easily fits within the 16.6ms frame budget).

## Follow-up
- File categorization rules engine (Phase 6): MVP Phase 4 uses a fast extension-based classification map in `storage-tree` / `treemap`.
- Treemap zoom animation: smooth transition animations when drilling down can be added via Win2D composition interpolation once baseline rendering is established.
